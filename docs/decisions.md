## 2026-08-18: 需要スコアは掛け算にせず、需要の「大きさ」と「充足度」を別の軸にする

- **決定**: 当初の予定表にあった `言及数 × 感情 × トレンド` の掛け算はとらない。以下の形にする

  ```
  需要の大きさ = トピックへの言及数（好意・不満を問わない）
  充足度       = そのトピックのポジ率
  トレンド     = 言及数の時間変化
  ```

- **理由**: 好意的なレビューも不満のレビューも、**どちらもその要素に需要があることを示している**。PvPしかないゲームで「PvEが欲しい」という声は満たされていない需要であり、「PvEが楽しい」という声はその需要が満たされている証拠になる。好意度を掛けると前者のスコアが低く出てしまい、「求められているのに応えられていないもの」を取り逃がす
- **副次的な理由**: 言及数（0〜数千）・ポジ率（0〜1）・トレンド（負にもなる）は単位も桁も揃っておらず、そのまま掛けると桁の大きい言及数だけで順位が決まる
- **成果物の形**: 1本のランキングか、大きさ×充足度の2軸マップか。**未確定**
- **却下した代替案**: 予定表通りの掛け算 → 上記の通り不満側の需要が消える

## 2026-08-18: 不満トピックを「需要」と「前提」に仕分ける方針とする

- **決定**: 不満を2種類に分け、需要スコアの対象を前者に限る
  - **満たされていない需要**（「PvEが欲しい」「内容が薄い」）… 作れば応えられる → 対象
  - **満たされていない前提**（クラッシュ・バグ・チーター・サーバー）… 直すべきもので、作る機能ではない → 対象外または別枠
- **理由**: 誰も「不具合が無いこと」をゲーム要素として求めているわけではない。仕分けをしないとランキング上位が不具合で埋まる。実際、現データの最大トピックは `crashes`（343件）であり、不具合は声が大きくなりやすいため件数で並べると必ず上位に来る
- **未確定**: 仕分けの具体的な方法（トピックを束ねる際の第一階層にする案がある）

## 2026-08-18: プレイ時間は「意見の信頼度」には使えるが「需要の強さ」の重みには使わない

- **決定**: レビューのプレイ時間を需要スコアの重み付けには使わない。使う場合は `playtime_at_review` を、ゲームごとの**中央値で割って正規化**する
- **理由**:
  - 重み付けは探している信号を消す。ある機能が無いゲームで「2000時間プレイして最高」という人と「3時間で離脱、その機能が無いので辞めた」という人がいた場合、プレイ時間で重み付けすると前者が600倍の重さになる。しかし**満たされていない需要を探すなら後者こそが目的の信号**であり、離脱者の声が消える
  - 混ぜると「満足している人が満足だと言っている」ことを確認するだけの指標になる
  - 正規化が必要なのは、100時間の意味が作品ごとにまるで違うため。平均ではなく中央値を使うのは、プレイ時間の分布が極端に偏っており少数の突出値が平均を引き上げるため
- **補足**: `playtime_forever` はレビュー後に遊んだ分を含むため、「どれだけ遊んだ上でこの意見を書いたか」を表さない。現在の収集コードはプレイ時間を破棄しているので、収集項目への追加は Issue #32 で検討する

## 2026-08-18: 需要の「結果」は観測できないため、需要スコアは検証不能な指標として扱う

- **決定**: 需要スコアの予測精度は検証できない前提で進める。検証したい場合は、同時接続数の定期記録を今日から始めて将来の検証データを自分で作る
- **理由**: Steam公式APIで取得可否を実測した結果、以下が判明した
  - **販売本数・DL数は取得できない**（Valveが非公開。`appdetails` に該当フィールドなし）
  - **同時接続数は現在値のみ**（`GetNumberOfCurrentPlayers`・APIキー不要）。過去の推移は返らない
  - 取得できるのはレビュー本文・投稿日時・累計ポジ率・プレイ時間・購入経路・返金の有無など、需要の「痕跡」のみ
  - つまり需要の「結果」を記録した正解データが存在せず、スコアが当たったか外れたかを判定できない
- **却下した代替案**: 第三者サイト（SteamSpy等）の推定値を正解とする → 推定値であり、精度の根拠を自分で説明できない

## 2026-08-18: Phase 7 は既存の reviews_10000.csv を使わず、時系列用に別データセットを収集する

- **決定**: 時系列予測用のデータは新規に収集する。既存の10,000件は感情分析モデルの学習用として残す
- **理由**: 既存データは感情分析用の設計（各ゲーム714件で打ち切り・Pos/Neg 50:50）で集めており、時系列に必要な性質を2つとも満たさない
  - 密度不足: 1トピック1日あたり0.12件。系列がほぼ0で埋まり傾向を読み取れない
  - 比率の歪み: 50:50を強制した結果、ネガ側にしか現れないトピックが水増しされている。**同じ集め方で件数を10倍にしても10倍の規模で同じだけ歪むだけ**で、増量では解決しない
- **却下した代替案**:
  - 既存データを増量する → 比率の歪みが直らない
  - 期間の長いゲーム（Stardew Valley・The Witcher 3）だけで代用する → 2本では需要の傾向として意味を持たない

## 2026-08-18: 自然比率とレビュー密度の実測（#31）を、収集スクリプト実装（#32）より先に行う

- **決定**: 調査を先、実装を後にする
- **理由**: 測定結果が実装の仕様（集計粒度・対象ゲーム数・遡る期間）を決めるため。先に実装すると、日次前提で作った後に密度不足が判明して作り直しになる。しかも測定コストはほぼゼロで、`query_summary` は既にAPIレスポンスに含まれており `steam_collector.py` が読み捨てているだけ（追加のAPI呼び出し不要・数十分の作業）。対して収集実装は数日規模
- **却下した代替案**: 収集しながら比率も測る → 収集の設計自体が測定結果に依存しているため順序が成立しない

## 2026-08-18: 収集処理はクラスではなく既存モジュールへの関数追加で実装する

- **決定**: `src/data/steam_collector.py` に関数を追加する。時系列用クラスは作らない。実行スクリプトは `scripts/collect/` に新規1ファイル
- **理由**:
  - 同モジュールは323行の関数ベースで**クラスが1つもない**。クラスを導入すると既存と作りが揃わない
  - `get_steam_reviews` は既に `filter='recent'`（投稿時刻の新しい順）+ cursorページングで動いており、件数で止めている箇所を日時で止める形に変えるだけでよい
  - 既存 `collect_balanced_reviews` は感情分析で使い続けるため壊さず、`review_type='all'` で1回呼ぶ兄弟関数を並べて置く
  - 実行スクリプトを分けるのは、既存が `collect_dataset_10k.py` / `collect_ood_testset.py` と用途別1ファイルの構成のため
