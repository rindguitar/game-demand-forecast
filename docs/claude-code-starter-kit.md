# Claude Code スターターキット（Opus効率運用・統合版）

CLAUDE.md本体とセットで使う付属ファイル群とプロンプト集。
新プロジェクト開始時は「1. 初期セットアップ」を一度だけ実行すれば以後のセッションは低コストで回る。

このキットは3層でコンテキストを管理する:
- **常時ロード**: `CLAUDE.md`（薄く保つ。毎セッション・トークンを消費するため）
- **条件付きロード**: `.claude/rules/*.md`（paths指定。該当ファイルを触るときだけロード）
- **状態**: `docs/STATUS.md`（変化する情報を規約とは分離して化石化を防ぐ）

---

## 1. 初期セットアップ（プロジェクト開始時に一度だけ）

```
mkdir -p docs .claude/agents .claude/rules
```

同梱の CLAUDE.md / docs/*.md / .claude/agents/*.md / .claude/rules/*.md を配置し、
各ファイルのプレースホルダをプロジェクトの実情で埋める。

`src/` `scripts/` `tests/` の README を初回に作る（規約は `.claude/rules/readme.md`）。

配置後の最初のセッションで必ず `/cost` と `/context` を確認すること（後述）。

---

## 2. ファイル構成

```
CLAUDE.md                     # 薄いインデックス（常時ロード）
docs/
  STATUS.md                   # 現在地・次の一手（作業のたびに更新）
  decisions.md                # 軽量ADR（設計判断の記録）
  experiments.md              # 実験結果・検証済みの知見
src/README.md                 # モジュール構成・依存関係（図あり）
scripts/README.md             # 実行順序・入出力（データフロー図）
tests/README.md               # テスト分類・実行方法
.claude/
  agents/
    explorer.md               # haiku: 探索・grep（読み取り専用）
    implementer.md            # sonnet: 承認済み方針の実装
    test-runner.md            # haiku: テスト実行・要約
  rules/
    python-tests.md           # テストファイル編集時のみロード
    readme.md                 # README編集時のみロード
    mermaid.md                # ドキュメント編集時のみロード
    wiki.md                   # Wiki更新時に参照
```

Wikiは本体とは別のGitリポジトリ（`<owner>/<repo>.wiki.git`）。
`.claude/rules/wiki.md` は paths が効かない場合があるため、CLAUDE.md の
「ドキュメント規約」から明示的に参照させておく。

## 3. ドキュメント運用（作業のたびに随時）

セッション終了時にまとめてではなく、**1タスク終わるごとに**回す:

1. `docs/STATUS.md` を更新
2. 設計判断があれば `docs/decisions.md` に追記
3. 触ったディレクトリの `README.md` を更新
4. 新しい技術概念・調査結果はWikiへ。Homeとドキュメントマップも更新
5. コミット・プッシュ

構造・流れ・依存関係の説明は文章で済ませずMermaid図にする。
**図は必ず画像に描き出して目視する**（構文が通ることと読めることは別物）。

---

## 4. サブエージェントについて（コスト削減の主レバー）

Opusのメインセッションから安価なモデルへ作業を逃がす。
効果は「安いモデルが動くから安い」だけでなく、**メインのコンテキストを汚さない**点にある
（テストの長い出力やgrep結果をメインに残すと、以降そのセッション中ずっと再送信され続ける）。

- モデルルーティングには既知の不具合報告があるため、導入後に一度 `/cost` で
  実際にsonnet/haikuへ流れているか確認すること。
- 確実性を上げたい場合は環境変数 `CLAUDE_CODE_SUBAGENT_MODEL` を併用
  （環境変数名は最新の公式ドキュメントで綴りを確認してから使う）。
- description は Claude が自動委譲の判断に使うため、具体的に書くほど効く

### 段階導入のすすめ（一人プロジェクトの場合）
3エージェントを最初から全部使うより、まず explorer(haiku) だけ入れて
効果を体感 → 効くなら implementer を足す。複雑さの割に効くか見極めやすい。

## 5. セッションプロンプト集

### 5-1. セッション再開（最頻出・これだけで始まる）
```
docs/STATUS.md を読んで、「次の一手」の1番から進めてください。
生成前に今日の作業ゴールを1-3行で確認してください。
```

### 5-2. 新機能・新フェーズの開始
```
新しいフェーズに入ります: 「（例）Prophetでレビューポジ率の時系列予測」

まだ実装せずに以下を提示してください:
1. 方針（アプローチの選択肢が複数あれば比較して推奨を明示）
2. 影響するファイル・新規作成するファイルの一覧
3. 作業を3-5ステップに分割した計画（各ステップは1セッションで完了する粒度）

私が承認したらステップ1のみ着手してください。
```

### 5-3. 設計レビュー（Opusの得意分野に集中させる）
```
（対象ファイル/設計）についてレビューしてください。観点:
1. 設計上の欠陥・見落としているエッジケース
2. 拡張性（次フェーズで――を足すとき問題ないか）
3. 過剰設計になっている箇所（シンプルにできる案）

コードの書き直しは不要です。指摘と理由のみを重要度順に。
```

### 5-4. デバッグ
```
（エラー/症状の説明。エラーメッセージは要点のみ貼る）

まず原因の仮説を確度順に2-3個挙げ、それぞれの検証方法を提示してください。
検証に必要な調査はexplorerサブエージェントを使ってください。
原因が確定するまで修正コードは書かないでください。
```

### 5-5. ドキュメント更新（1タスク終わるごと）
```
このタスクは完了です。ドキュメントを更新してください:
- docs/STATUS.md（現在地・次の一手）
- 設計判断があれば docs/decisions.md
- 触ったディレクトリの README.md（図が実態とずれていないか確認）
- 新しい概念が出たならWikiのページとHome、ドキュメントマップ
図を更新したら画像に描き出して交差・貫通を確認してください。
```

### 5-6. セッション終了
```
今日はここまでにします。未反映のドキュメント更新があれば済ませて、
コミット・プッシュ漏れがないか確認してください。
```

### 5-7. コンテキストが重くなってきたとき
```
このセッションのこれまでの作業内容と決定事項を docs/STATUS.md に反映してください。
反映後、新しいセッションで続きをやります。
```
（→ `/clear` して 5-1 から再開）

## 6. 運用のコツ（人間側）

- **1セッション1目的**。目的を跨ぐならSTATUS.mdを更新して新セッションへ
- **巨大な履歴を引きずらない。** `--continue` / resume で数十万トークンの履歴を再開すると、
  1通目でその全量が再送信される。再開はSTATUS.md経由で新セッションを立てる
- `/context` の Messages が **200kに近づいたら**切り替えを検討する
  （入力200k超は割増レートの領域）。固定費（CLAUDE.md・ツール定義等）は数%しかないので、
  `/clear` の作り直しコストは小さい
- **`/compact` はタダではない。** 履歴全体を入力して要約を作るため、遅らせてから持つと高い。
  デフォルトは「STATUS.md反映 → `/clear`」。`/compact` はタスクのど真ん中で
  切り上げられないときだけ、早め（100-150k程度）に打つ
- 計画立案には**Planモード**（Shift+Tab）を使う。実装前の思考にファイル編集権限は不要
- STATUS.mdが肥大化してきたら、古い内容はdecisions.mdやexperiments.md、Wikiへ移して、現在地だけに保つ
- 規約が増えてきたら CLAUDE.md に足さず、`.claude/rules/` にトピック別ファイルを作る
- Claudeに同じ指摘を2回したら、その場で `#` から始めて即追記する
- このキット自体も自分のプロジェクトに合わせて削る・足す
