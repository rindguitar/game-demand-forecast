# Mermaid図の作成手順

READMEとWikiに図を追加・更新するときの手順と原則。

2026-08-27にREADMEとWikiの図を作った際、**読みにくさを指摘されて3回作り直した**。
そのとき分かったことを、次に同じ失敗をしないために残す。

---

## 図の3原則

### 1. 矢印は、向きが情報のときだけ使う

| 図 | 矢印 | 理由 |
|---|---|---|
| `scripts/README.md` のデータフロー | **使う** | 「このCSVが次の入力になる」という向きが図の中身そのもの。消すと何も分からなくなる |
| Wikiのドキュメントマップ | **使わない** | 「関連している」ことしか表していない。向きは表に書けば足りる |

矢印は情報を1つ増やすが、読む負荷も増やす。**その向きが無いと図が成立しないか**で判断する。

### 2. 略称を図に置かない

`DAPT` `OOD` `MLM` のような略称をそのまま置かない。図は一瞬で読む前提なので、
略称を頭の中で展開する手間が入るとそこで止まる。

```
悪い: DAPT
良い: ドメイン適応事前学習<br/>DAPT
```

日本語を上、略称を下に添える。ラベルが2行になるが、そのほうが読める。

### 3. 1枚の線を減らす

交差するかどうかは、ほぼ**1枚あたりの線の本数**で決まる。
16ページ33本の図はどう並べても交差する。実測では**1枚10本前後**が上限だった。

---

## 交差を減らす手順（この順で試す）

### 手順1: まとめる（最優先）

密に繋がりあうものを1つの箱にまとめる。箱の中の線は図から消えるので、線が大きく減る。

Wikiで実際にやったとき、38ノード68線が **4ノード5線** になった。

**まとめる方が、分けるより上位**である理由: 分割は全体像を失うが、まとめても全体像は残る。
「まとめた図（全体像）＋ 箱ごとの図（内訳）」の2階層にすれば、どちらも見られる。

### 手順2: 分ける

まとめてもまだ多いなら、内訳をさらに分ける。分けるときは**番号を振り、見出しと対応させる**。
図に「ブロック3」とあれば「## ブロック3」の節に飛べる、という状態にする。

### 手順3: ほぼ全結合なら、図にしない

全ペアの8割以上が繋がっているまとまりは、描いても線が絡むだけで情報が伝わらない。
**一覧＋「繋がっていない組」の明記**に置き換える。

```
この5ページは互いにほぼ全部繋がっています（10通りのうち9通り）。
- ページA
- ページB
...
唯一繋がっていない組: ページC と ページE
```

### 図から落とした線は、必ず本文で補う

分けたりまとめたりすると、描かれない線が出る。**その線を表や文章で残す。**
図を読みやすくするために情報を捨ててはいけない。

---

## 必ずやること: 画像に描き出して目で見る

**構文チェックが通ることと、読めることは別物。**
`mermaid.parse()` が通っても、線がノードを貫通していれば誤読される。

実際に「AとBが繋がっているように見えるが、間にCがあって判断できない」という指摘を受けた。
その線は本物の接続だったが、図が誤読を誘っていた。

### 準備（初回のみ）

```bash
# 描画ツール
npm install -g @mermaid-js/mermaid-cli

# 日本語フォント（WSLの場合はWindows側から借りる）
cp /mnt/c/Windows/Fonts/meiryo.ttc ~/.local/share/fonts/
fc-cache -f
```

WSL/Docker環境ではサンドボックスを切る必要がある。設定ファイルを1つ作っておく。

```bash
echo '{"args":["--no-sandbox","--disable-setuid-sandbox","--disable-dev-shm-usage"]}' > /tmp/pconf.json
```

### 描き出して見る

```bash
mmdc -i fig.mmd -o fig.png -p /tmp/pconf.json -b white -s 2
```

生成されたPNGを開いて、次の2つを確認する。

- **交差**: 線と線が交わっていないか
- **貫通**: 線がノードの箱の上を通っていないか（交差より誤読を招く）

### 並び順を変えると結果が変わる

Mermaidは**辺を宣言する順序でレイアウトが変わる**。交差が出たら、順序を入れ替えた版を
2〜3個作って描き比べ、いちばん綺麗なものを採用する。

「線が少ない順に並べる」のような機械的なルールでは交差ゼロを保証できなかった。
**描いて見比べるのが確実。**

## 手順A: READMEの図を作る・更新する

READMEの図は「処理の流れ」なので、ディレクトリや処理の単位ごとに割れば交差はほぼ消える。

1. 対象のスクリプト・モジュールの依存を実測する（`grep` で import と入出力パスを拾う）
2. **推測で描かない。** 実測結果と表の記述が食い違ったら、実測が正しい
3. 処理の単位ごとに図を分ける。全体は4段程度の粗い流れだけにする
4. 図形を統一する — 四角＝スクリプト / 円筒 `[( )]` ＝データ / 六角形 `{{ }}` ＝モデル
5. 線が増えて読みにくくなる要素（複数の図に共通する入力など）は図から外し、本文で補う
6. 画像に描き出して目視
7. コミット

現状は `scripts/README.md` に9枚、`src/README.md` に3枚、`tests/README.md` に2枚ある。
1枚あたり最大7本に収めてある。

## 手順B: Wikiのドキュメントマップを作り直す

**Wikiにページを追加したりリンクを張り替えたら、[ドキュメントマップ](https://github.com/rindguitar/game-demand-forecast/wiki/Documentation-Map)も作り直す。**
元データが変わると図が実態とずれ、「どのページが孤立しているか」を見るという本来の用途が壊れる。

作業自体は機械的なので、Claude Codeに依頼するのが早い。手順は次のとおり。

### 1. Wikiをcloneする

```bash
git clone https://github.com/rindguitar/game-demand-forecast.wiki.git /tmp/wiki
```

### 2. ページ間のリンクを抽出する

各ページ本文の `](ページ名)` を走査し、リンク先がWiki内のページ名と一致するものだけを拾う。
向きは落とし、往復しているものは1本に畳む。

```python
import os, re
d = '/tmp/wiki'
skip = {'Home', 'Documentation-Map'}
pages = {f[:-3]: open(os.path.join(d, f), encoding='utf-8').read()
         for f in os.listdir(d) if f.endswith('.md')}
edges = {tuple(sorted((src, t.split('#')[0].strip())))
         for src, txt in pages.items() if src not in skip
         for t in re.findall(r'\]\(([^)]+)\)', txt)
         if t.split('#')[0].strip() in pages
         and t.split('#')[0].strip() not in skip | {src}}
print(len(pages), 'ページ /', len(edges), '本')
```

### 3. 密に繋がるまとまりを見つける

貪欲モジュラリティ最大化（隣り合うまとまりを、モジュラリティが上がる限りくっつけていく）で
ブロックを検出する。**分類を人が決めない**ことが大事で、そうすることで
「Homeの分類と実際のリンクがずれている」といった発見が出る。

### 4. 図を組む

上の「交差を減らす手順」に従う。全体地図 → ブロックごとの内訳、の2階層にする。
ブロックの名前だけは中身を見て人が付ける。

### 5. 画像に描き出して、全枚数を目視する

省略しない。1枚でも貫通していれば誤読される。

### 6. pushして、Homeの更新履歴に1行足す

```bash
cd /tmp/wiki && git add -A && git commit -m "docs: ..." && git push
```
